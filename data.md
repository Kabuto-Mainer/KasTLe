Окей. Слой 2 — это кодировщик, который превращает `KTL_BackIR_Item` (один айтем за раз) в байты x86_64. Это самый объёмный кусок проекта по количеству knowledge'а, который надо в голове удержать. Дам общую картину, потом пройдусь по архитектурным решениям, потом по неприятным сюрпризам, потом — с чего реалистично начать.

## Что вообще представляет собой инструкция x86_64

Любая инструкция — это последовательность из шести логических частей, каждая из которых может быть пустой:

```
[Legacy prefixes 0..4] [REX 0..1] [Opcode 1..3] [ModR/M 0..1] [SIB 0..1] [Disp 0/1/2/4] [Imm 0/1/2/4/8]
```

В сумме до 15 байт. Большая часть твоего кодировщика — это решение «какой опкод выбрать для конкретной комбинации операндов» и «какие ModR/M, SIB, displacement, immediate под него выкатить». Это **не один опкод на одну инструкцию**: у `mov` минимум 10 разных кодировок в зависимости от того, что слева и что справа. Поэтому подход «таблица: enum → байты» (как у тебя сейчас в `OPCODES_NO_ARG`) работает только для инструкций без операндов. Для всего остального этого мало.

Внутренние подкомпоненты, которые понадобятся буквально везде:

- **REX** — однобайтовый префикс `0100 WRXB`. W=1 для 64-битных операций, R/X/B — расширения, чтобы дотянуться до регистров r8-r15. Эмитится только если хотя бы один бит ненулевой (плюс несколько специальных случаев).
- **ModR/M** — байт `mm rrr bbb`. Главный байт, описывающий «куда» и «откуда». `mod` определяет режим адресации (регистровый / память / память+disp8 / память+disp32). `reg` — это либо номер регистра-операнда, либо «расширение опкода» (когда у инструкции мало форм, но различаются операции — как `add` vs `or` vs `sub` с одним и тем же опкодом 0x83, но разным `reg`).
- **SIB** — байт `ss iii bbb`, нужен для адресации `[base + index*scale + disp]`. Появляется когда ModR/M это требует.
- **Displacement** — смещение в памяти (8 или 32 бита, little-endian, со знаком).
- **Immediate** — константа (8/16/32/64 бита, little-endian).

Вот эти пять примитивов — основа всего. Кодирование любой инструкции сводится к: «выбрать опкод → правильно собрать REX → правильно собрать ModR/M (плюс возможно SIB) → дописать disp и imm».

## Архитектурные решения, которые надо принять сейчас

### 1. Per-instruction функции vs unified table

Два подхода:

**Per-instruction.** На каждый мнемонический enum (`KTL_ASM_MOV`, `KTL_ASM_ADD` и т.д.) — своя функция-кодировщик. Внутри switch по комбинациям типов операндов: reg-reg, reg-mem, reg-imm, mem-reg, mem-imm. Каждая ветка собирает байты через общие хелперы (emit_rex/modrm/sib/imm).

**Table-driven.** Большая таблица `(instr, operand_pattern) → encoding_rule`, где encoding_rule описывает декларативно: «опкод такой, REX.W нужен, /digit такой, immediate берётся отсюда». LLVM, GCC, NASM делают примерно так.

Для **30 инструкций**, как у тебя — однозначно per-instruction. Таблично-декларативный подход стоит начинать только когда у тебя сотни инструкций или когда ты автогенерируешь из спецификации Intel SDM. Сейчас это overengineering.

### 2. Как выбирать «форму» инструкции

Для одной мнемоники типа `mov` нужно сматчить по типам операндов. Внутри `encode_mov` твой switch будет на парах операнд-видов:

```
(REG, REG)        → опкод 89
(REG, IMM)        → опкод B8+r (REX.W если 64-битно)
(REG, MEM)        → опкод 8B
(MEM, REG)        → опкод 89
(MEM, IMM)        → опкод C7
(REG, MEM_RIP)    → опкод 8B + RIP-relative ModR/M
(MEM_RIP, REG)    → опкод 89 + RIP-relative ModR/M
```

И так далее. Часто разные ветки сводятся к общему помощнику. Например, для `mov reg, mem` и `mov reg, mem_rip` опкод одинаковый — отличается только ModR/M. Можно унифицировать.

### 3. Куда пишутся байты

То же решение, что для принтера: используй `cont->cur_out.cur_buf`. Для `.text` это инструкции, для `.data`/`.rodata` это «инструкций нет, есть только data-айтемы и метки». Поэтому функция-диспетчер `encode_item(item, buf)` смотрит на `item->kind`:

- `INSTR` → полный кодировщик инструкции
- `DATA_ZERO` → дописать N нулевых байт
- `DATA_INT` → дописать N байт little-endian (1/2/4/8)
- `DATA_BYTES` → memcpy сырых байт
- `DATA_SYMBOL` → N нулевых байт + запись релокации
- `LABEL` → не пишет байт, регистрирует «метка X указывает на текущий offset буфера»
- `DIRECTIVE(ALIGN)` → дописать NOP'ы или нули до выравнивания
- `COMMENT` → игнорировать (комментарии — артефакт текстового вывода, в бинаре их нет)

То есть **принтер и кодировщик имеют одну и ту же диспетчерскую структуру** — отличается только «что делать с каждым видом айтема». Это удобно: можно их даже сделать через одну функцию обхода с двумя разными колбэками. Но не обязательно — копипаста проще читается.

### 4. Forward references и таблица fixup'ов

Самая нетривиальная часть. Когда ты кодируешь `jmp .L0`, и `.L0` ещё не определена (forward jump), ты не знаешь смещения. Стандартное решение:

**Таблица меток + таблица fixup'ов.**

- При определении метки (`ITEM_LABEL`) — записываешь `labels[name] = current_offset`.
- При ссылке на метку из инструкции (`jmp/jz/jnz/call/lea`) — если метка известна (backward), сразу считаешь disp = `labels[name] - (cur_offset + sizeof(instr))`. Если неизвестна (forward) — пишешь 4 нулевых байта и в `fixups` кладёшь запись `{patch_at: cur_offset, target: name, kind: PC32}`.
- После обхода всего буфера проходишь по `fixups`: для каждого ищешь `target` в `labels`, считаешь disp, патчишь 4 байта в нужной позиции.

Любая ссылка, оставшаяся неразрешённой после этого прохода (например, `call printf` — printf не определён в этом объектнике) превращается в **ELF-релокацию** для линкера.

### 5. rel8 vs rel32 для jump'ов

Маленькая оптимизация, но архитектурно важная. У x86 есть две формы условных переходов: `jz rel8` (2 байта) и `jz rel32` (6 байт). Аналогично безусловный `jmp rel8` (2 байта) и `jmp rel32` (5 байт). Если бы все переходы можно было закодировать rel8 — код был бы заметно компактнее.

Но: **на момент кодирования forward jump'а ты ещё не знаешь, попадает ли target в ±128 байт.** А если не попадает — нужно перекодировать в rel32, а это меняет размер инструкции, что сдвигает все последующие смещения, что может перевести другие jump'ы из rel8 в rel32, и т.д.

Способы:

- **Пессимистический.** Всегда rel32. Просто, но теряешь несколько байт на каждом jump'е. **Я рекомендую начать с этого.**
- **Двухпроходный.** Первый проход эмитит всё в rel32 + собирает таблицу позиций. Второй проход смотрит реальные расстояния и сжимает где можно. Чуть-чуть сложнее.
- **Итеративный.** Гонять циклом до сходимости. Это уже взрослый assembler-уровень.

### 6. Релокации vs внутренние fixup'ы

Не всякая ссылка резолвится у тебя внутри. У тебя четыре подвида символов в IR:

- `LOCAL_FUNC` — функция в этом же объектнике. Ссылка из `call` → внутренний fixup, считаем disp32 от call'а до начала функции. Никакой релокации.
- `GOT_FUNC` — функция в другом объектнике (libc). `call printf` → пишем 4 нулевых байта + ELF-релокация `R_X86_64_PLT32` с символом `printf`.
- `LOCAL_VAR` — глобальная переменная в этом же объектнике. Доступ через RIP-relative → 4 нулевых байта + релокация `R_X86_64_PC32` (или внутренний fixup, если упрощаешь и уверен что секция .data в одном файле).
- `GOT_VAR` — внешняя переменная. Доступ через GOT → релокация `R_X86_64_GOTPCRELX`.

Локальные метки (`OP_LABEL` в IR) — это всегда внутренний fixup, никогда не релокация. Они существуют только внутри одной функции и не попадают в symtab.

Поэтому архитектурно у тебя в кодировщике **две сущности**: `KTL_Fixup` (внутренние, патчатся в конце прохода) и `KTL_Reloc` (внешние, попадают в `.rela.text` ELF'а). Часть путей кодирования пишет первую, часть — вторую. У тебя `KTL_BackIR_SymbolKind` уже разделяет эти случаи — отлично.

### 7. Структура состояния кодировщика

Помимо буфера байтов нужно держать:

- **Таблица меток**: `name → offset` в текущей секции.
- **Таблица fixup'ов**: список `{patch_offset, target_name, size, kind}`.
- **Таблица релокаций**: список `{offset, symbol, addend, reloc_type}`.

Минимум одна тройка на каждую секцию (`.text`/`.data`/`.rodata`). Логично сделать `KTL_Section { bytes, labels, fixups, relocs }` и держать три экземпляра.

## Сюрпризы x86_64, которые надо знать заранее

Иначе наступишь на каждый из них по очереди и потеряешь полдня на каждом.

**1. rsp требует SIB.** Bottom 3 бита rsp = `100`, что в поле `r/m` означает «следующий байт — SIB». То есть `mov rax, [rsp]` требует SIB-байт даже без индекса (там пишется `[rsp + 0*]`, формально SIB.index=100=NONE, SIB.base=rsp). Если просто эмитнуть ModR/M с rm=100 — процессор подумает, что дальше SIB, и считает не то.

**2. rbp при mod=00 — это не [rbp].** Bottom 3 бита rbp = `101`. В 64-битном режиме комбинация mod=00, rm=101 означает **RIP-relative addressing** (`[rip + disp32]`). Поэтому чтобы реально закодировать `[rbp]` без смещения, надо использовать mod=01 с disp8=0. То есть `[rbp + 0]` всегда занимает на 1 байт больше, чем `[rax]`.

**3. r12 и r13 наследуют эти проблемы.** r12 = `100` в нижних 3 битах = ведёт себя как rsp (требует SIB). r13 = `101` = ведёт себя как rbp при mod=00 (нельзя без disp). REX.B=1 — это просто «4-й бит регистра», нижние 3 бита остаются те же.

**4. /digit нотация.** В таблицах Intel пишут `ADD r/m32, imm8 → 83 /0 ib`. Это значит: опкод 83, в поле ModR/M.reg ставишь 0 (это «extension» для отличения add от or/sub/cmp/and/xor — все они имеют опкод 83 с разными /digit). Значит для **многих** инструкций ModR/M.reg — это **не регистр**, а часть опкода. Когда пишешь кодировщик `add reg, imm32` — ModR/M = `mod:11 reg:000 rm:dst`. А когда пишешь `add reg, reg` — там уже `mod:11 reg:src rm:dst`. Это две разные ситуации с одним и тем же ModR/M-байтом.

**5. Опкод+регистр.** Некоторые опкоды имеют форму `B8+rd id` — это значит «опкод 0xB8, плюс номер регистра в нижних 3 битах самого опкода». Например, `mov rax, imm64` = `48 B8 ...`, `mov rcx, imm64` = `48 B9 ...`. Никакого ModR/M. И REX.B расширяет «номер регистра в опкоде» точно так же, как rm. Эта форма дает один из вариантов кодирования `mov reg, imm` и она самая компактная — её стоит использовать когда возможно.

**6. Размер операнда и префиксы.** В 64-битном режиме:
- 32-битные операции: дефолт, ничего не нужно.
- 64-битные операции: REX.W=1.
- 16-битные операции: префикс `66h`.
- 8-битные операции: обычно опкод-1 от 32-битной формы (например, `mov r/m, r` это 89 для 32-битного и 88 для 8-битного).

Плюс есть случай байтовых операций с regs spl/bpl/sil/dil (нижние байты rsp/rbp/rsi/rdi) — для них **обязательно** нужен REX (даже пустой), иначе кодировщик считает, что это ah/ch/dh/bh.

**7. Эффективная длина disp выбирается по значению.** `[rbp - 16]` лучше кодировать как mod=01 disp8=-16 (1 байт), а не mod=10 disp32=-16 (4 байта). При этом `[rbp - 200]` уже не влезает в disp8 (диапазон −128..+127), нужен disp32. Логика выбора: если влезает в `int8_t` — disp8, иначе disp32. Кроме случая mod=00 для rbp/r13 — там всегда нужен хоть какой-то disp.

## С чего реалистично начать

Чтобы не утонуть, я бы шёл так. **Один день — одна группа инструкций**, в каждом цикле полная процедура:

1. Написать кодировщик.
2. Скомпилировать тестовую программу через свой компилятор → получить буфер байтов.
3. Скомпилировать ту же программу через `nasm -f elf64` → получить эталон.
4. `xxd` оба, `diff`. Несовпадения — баг в кодировщике.

Порядок (от простого к сложному):

1. **Безоперандные**: `ret`, `syscall`, `cdqe`, `cqo`, `rep stosb`, `rep movsb`. Это просто таблица «инструкция → готовые байты» — у тебя такая уже есть. Закроешь за час.

2. **`mov reg64, imm32` и `mov reg64, reg64`.** Самые частые формы. Заодно отладишь REX.W и базовый ModR/M.

3. **`push reg64` / `pop reg64`.** Опкод+регистр (50+r / 58+r), без ModR/M. Хорошо для проверки, что REX.B работает.

4. **Арифметика на регистрах**: `add/sub/xor/and/imul reg, reg`, `neg reg`, `cmp reg, reg`, `test reg, reg`. Все одинаково устроены, отладишь /digit и общие хелперы.

5. **Mem-операнды на rbp**: `mov [rbp+disp], reg`, `mov reg, [rbp+disp]`. Здесь споткнёшься о rbp-mod-00 проблему, отладишь. После этого расширишь на любой base + disp.

6. **rsp с SIB**: `mov [rsp+disp], reg`. Проверишь, что SIB-эмит работает.

7. **`mov reg, imm` для разных размеров и `add reg, imm`** — пара форм с /digit.

8. **Jump'ы**: `jmp`/`jz`/`jnz` с rel32. Тут впервые появятся fixup'ы. Отладишь backward jumps на простом `while`. Forward — на простом `if`.

9. **`call sym`** — то же самое, плюс первая ELF-релокация.

10. **RIP-relative `mov reg, [rel name]`** — для глобалов и строковых литералов. Тут вторая категория релокаций.

11. **Сложная адресация `[base + idx*scale + disp]`** — для массивов. Полный SIB.

12. **`lea`** — обычно тривиально после mem-операндов, потому что `lea` использует тот же ModR/M+SIB механизм, просто с другим опкодом.

13. **`movzx`/`movsx`** — мульти-байтовые опкоды (0F-prefixed).

14. **`setcc`** — однобайтные, но 0F-prefixed.

После 14-го пункта у тебя закрыты все инструкции, которые порождает твой компилятор. Дальше — ELF-writer (слой 3): берёт готовые байты, fixup'ы, релокации, метки, и сериализует в `.o` файл с правильными заголовками.

## Что я бы сделал прямо в ближайшую сессию

Прежде чем браться за инструкции — оформить **скелет кодировщика и инфраструктуру байтового вывода**. Это не сложно и даст тебе площадку, на которой все остальные шаги будут стандартными:

- Структура `KTL_Section { bytes, labels, fixups, relocs }`.
- Хелперы: `emit_byte`, `emit_bytes`, `emit_le16/32/64`, `emit_rex`, `emit_modrm`, `emit_sib`.
- Функции `add_label(section, name)`, `add_fixup(section, target_name, size)`, `resolve_fixups(section)`.
- Функция-диспетчер `encode_item(section, item)` с пустыми ветками для всех видов айтема — чтобы каркас компилировался и пропускал пустой буфер. Дальше каждый день закрываешь по одной ветке/инструкции.
